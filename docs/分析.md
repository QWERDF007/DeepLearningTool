# DeepLearningTool 代码结构分析

## 结论

DeepLearningTool 是一个由 Qt 6/QML 驱动界面、C++20 驱动业务、SQLite 驱动持久化、Python/EasyTrain 驱动模型任务的桌面应用。

核心架构关系：

```text
QML 页面
  -> ProjectManager / Project
      -> DataManager / ModelManager / FeatureManager / TaskManager
          -> database 门面与 Qt Model
          -> 后台工作流
              -> 文件与数据准备
              -> ExternalModelTaskRunner
                  -> EasyTrain / Python
              -> TCP 任务事件 / 评估结果
```

`Project` 是项目级聚合根，负责当前项目对象的所有权和关闭顺序；`database` 是 SQLite 访问边界；`data`、`model`、`feature` 是主要领域业务模块；`tool` 负责应用装配和顶层 QML 导航。

事实源优先级：构建关系以 CMake 为准，数据库结构以 DDL 和数据库实现为准，模型/设置参数以 YAML 和解析实现为准，公开接口以头文件为准，本文只提供结构导航和风险索引。

## 2. 构建目标和依赖

源码装配顺序位于 [`src/CMakeLists.txt`](../src/CMakeLists.txt)：

```text
common
  -> core
  -> database
  -> ui
  -> parameter
  -> settings
  -> data
  -> model
  -> feature
  -> project
  -> tool
```

该顺序是子目录装配顺序，不是严格的线性依赖图。主要 target 关系如下：

```text
dltool_common
├── dltool_core
├── dltool_database
├── dltool_ui
├── dltool_parameter
└── dltool_settings
      └── dltool_data
            └── dltool_model
                  └── dltool_feature

dltool_project
└── 聚合 ui / core / data / feature / database / settings / common / model

dltool
└── 链接全部业务模块并装配 QML
```

第三方运行时和构建依赖包括：

- Qt 6：Core、Gui、Quick、QML、Widgets、Charts、Network、WebEngineQuick、QuickTest。
- SQLite/sqlpp11：数据库连接、查询和事务。
- yaml-cpp：设置及模型参数解析。
- spdlog：应用和模块日志。
- OpenCV：图像、几何、Mask 和轮廓处理。
- InferRT、FAISS、CUDA：推理、特征搜索和聚类。
- nlohmann/json：数据导入导出和任务扩展数据。
- EasyTrain/Python：外部训练、推理和任务协议。

通用 CMake helper [`cmake/AddPluginLibrary.cmake`](../cmake/AddPluginLibrary.cmake) 负责模块目标、导出头、QML module 和安装规则；`common`、`database`、`parameter` 不生成 QML module。

## 4. 应用启动和项目生命周期

启动流程：

```text
src/tool/main.cpp
  -> CrashHandler::setup
  -> QtWebEngineQuick::initialize
  -> QApplication
  -> spdlog / UILogger
  -> QQmlApplicationEngine
  -> evaluationthumbnail provider
  -> 加载 qrc:/qt/qml/dltool/tool/qml/Main.qml
  -> 设置 ProjectManager 的 QML engine
```

项目创建或打开流程：

```text
ProjectManager
  -> Project::isValid
  -> ProjectDataBase 初始化或打开
  -> Project::init
      -> TaskManager
      -> DataManager
      -> ModelManager
      -> ModelTaskController
      -> ModelTestTaskManager
      -> FeatureManager
  -> currentProjectChanged / projectActivated
```

`Project` 以 QObject parent 管理项目级对象，不向 QML 暴露数据库对象。项目关闭由 [`Project::shutdown()`](../src/project/Projects.cpp) 统一组织：

```text
beginShutdown / requestShutdown
  -> FeatureManager
  -> ModelTaskController
  -> ModelTestTaskManager
  -> ModelManager
  -> DataManager
  -> TaskManager
  -> ProgressManager::reset
  -> 释放 Project 及数据库
```

关闭顺序中的控制器各自负责停止线程、取消令牌、外部进程和评估工作；完成、失败、停止之后的迟到回调不得重新打开终态任务。

## 5. 持久化模型

应用级数据库：

```text
应用目录/db/
├── settings.db
└── history.db
```

项目数据库：

```text
<project>.dlpro
├── project
├── datasets
├── images
├── label_classes
├── labels
├── tag_classes
├── tags
└── models
```

模型和任务数据库：

```text
models/<model>/model.db
├── train_params
├── datasets
└── test_tasks

models/<model>/test/<task>/task.db
├── task_info
├── test_params
├── datasets
└── prediction
```

数据库 DDL 正本位于 [`src/database/include/database/ddl/`](../src/database/include/database/ddl/)，由 [`DatabaseSchema`](../src/database/DatabaseSchema.cpp) 通过 Qt resource 加载和校验。

数据库访问边界：

- `ProjectDataBase` 负责项目库门面及跨表原子操作。
- `RecentProjectsDataBase` 负责 `history.db`。
- `SettingsDataBase` 负责动态设置表。
- `ModelDataBase` 负责模型级参数、数据集选择和测试任务索引。
- `ModelTaskDataBase` 负责任务信息、测试参数、数据集选择和预测记录。
- Repository 通过 `DatabaseContext` 使用连接，不自行决定事务。
- 评估结果和图表主要保存在当前进程的 ViewModel，不写入新的评估报告格式。

## 6. 数据工作区

```text
QML 页面
  -> DataManager
      ├── Qt Model
      ├── GlobalFilter
      ├── Statistics
      ├── DataImporter / DataExporter
      └── ProjectDataBase
```

`data` 提供：

- 数据集、图片、标签类别、标注实例和图片/标注标签。
- Gallery、Label、Review 页面。
- Folder、Mask、LabelMe、COCO 数据导入导出。
- 检测框、分割多边形和异常标注数据。
- 数据集划分、文件复制和聚类结果写回。
- 全局过滤、选择、统计和图片搜索结果过滤。

数据导出和文件操作通过 `DataOperationWorkflow` 执行：

```text
GUI 线程构造 DatasetExportSnapshot
  -> worker 接收路径和纯值快照
  -> worker 创建独立 ProjectDataBase
  -> 执行导出/复制/划分/写回
  -> queued completion 回 GUI
```

`DatasetIO` 提供公共文件扫描、图片尺寸读取、bbox/points 转换和路径处理。导入格式的具体实现由 `DataImporter`/`DataExporter` 扩展。

## 7. 模型任务、Python 和评估

普通任务链：

```text
模型页 / 任务中心
  -> ModelTaskController
  -> TaskManager::startTask
  -> Preparing
  -> ModelTaskPreparation
      -> 数据集导出
      -> 文件列表生成
      -> model.db / task.db 写入
      -> ExternalProcessSpec
  -> ExternalModelTaskRunner
  -> EasyTrain / Python
  -> TCP TaskCommunication
  -> TaskManager
  -> ModelManager / QML
```

任务状态：

```text
Pending
  -> Preparing
  -> Running
  -> Stopping
  -> Stopped / Finished / Failed
```

跨进程身份由以下三项共同确定：

```text
project_id + task_id + run_id
```

Python 任务通过 `3rdparty/EasyTrain/src/python/task/` 的协议发送状态、进度、日志和完成/失败/停止事件。`TaskManager` 会校验项目、任务和当前运行身份，终态任务不会被迟到消息重新打开。

评估链路：

```text
test.txt + task.db + project .dlpro + pred/*
  -> IEvaluationEngine
  -> EvaluationResult
  -> ModelEvaluationViewModel
  -> QML 评估面板、图表、混淆矩阵和实例列表
```

当前内置评估引擎为异常检测、目标检测和分割。检测/分割共享实例匹配骨架，异常检测读取 TIFF 分数图并构造图像级指标、阈值结果和异常区域。

## 8. Feature 高级能力

### 图像和 ROI 搜索

```text
ImageSearchController / RoiSearchController
  -> DataProvider
  -> InferRT 特征提取
  -> FAISS 索引
  -> DataManager.GlobalFilter
```

### 图像和 ROI 聚类

```text
ImageClusterController / RoiClusterController
  -> InferRT 特征
  -> 聚类
  -> DataManager 写回
  -> 数据集复制或移动
```

### 智能标注

```text
SmartAnnotationController
  -> SAM predictor
  -> mask
  -> polygon 后处理
  -> QML 标注结果
```

### DINO 区域检索

```text
RegionSearchController
  -> checkNeedsBuild（校验 index.yaml 契约与 index_scope.yaml 覆盖）
  -> [需建库] InferRT DinoRegionSearch::buildIndex（Encode -> Quantize -> Cluster -> Save）
  -> InferRT DinoRegionSearch::search（Fusion -> FineMatch -> FineExtract -> Output）
  -> 候选边界框去重并生成标注实例写入 DataManager
```

- 强契约校验包含 `model_name`、`weights_id`、`encoder_edge`、`view_overlap`、`quantize_int8`，参数不符或范围缺失时提供详细的 `buildReason` 诊断。
- 参数由 Profile YAML 模板与 11 个独立分组控制，支持切换 Profile 自动刷新 UI。
- 检索过程由单调递增阈值节流器提供平滑进度反馈。

### 小样本学习

FS-SAM2 复用普通模型任务链，不维护独立任务框架：

```text
FewShotLearningController
  -> 隐藏 FS-SAM2 ModelRecord
  -> 普通 train/test 参数
  -> BoxToMask
  -> Train
  -> Test
  -> DataManager.importMaskData
```

## 10. 测试和验证结构

测试统一由 CTest 注册和执行：

| 类型 | 目录 | 标签 | 关注点 |
| --- | --- | --- | --- |
| 公共基础 | `tests/common`、`tests/database` | `ordinary` | 异步、几何、schema、Repository |
| UI | `tests/ui` | `ordinary;ui` | UI 工具和进度服务 |
| Data | `tests/data` | `ordinary;data` | 数据格式、导入导出、划分和工作流 |
| Model C++ | `tests/model` | `ordinary;model` | 任务、模型、参数、评估和存储 |
| Model QML | `tests/model_qml` | `ordinary;qml` | 评估面板、缩略图、状态和 QML 交互 |
| 项目级 | `tests/project` | `project;...` | `.dlpro`、真实文件、模型任务和评估链路 |

项目级测试由 `PersistentProjectFixture` 提供项目目录、数据库、图片、Mask 和模型任务环境。`tools/run_project_tests.py` 通过 fixture 选择完整流程或单一层级。

重点覆盖：

- 数据库 schema 初始化、校验、迁移回滚和 Repository 事务。
- 数据导入导出、格式 roundtrip 和数据集划分。
- TaskManager 状态、TCP 协议、外部进程和关闭生命周期。
- 模型参数、模型存储、数据集组织和评估引擎。
- QML 评估面板和部分 UI 生命周期。
- PatchCore 项目级训练、预测和评估流程。

系统性覆盖不足：

- 完整人工桌面 UI 操作链路。
- GPU、CUDA、InferRT 和硬件差异。
- 损坏数据库、损坏图片和极大数据集。
- 所有 Python 失败、取消和异常退出场景。
- QML engine teardown、多项目隔离和所有 provider 生命周期。

## 11. 架构优点

1. `Project` 统一项目级对象所有权和关闭顺序，避免页面自行管理生命周期。
2. `ModelTaskRequest`、`TaskIdentity`、`ModelEvaluationOptions` 和 `EvaluationResult` 将跨线程/跨进程数据显式化。
3. 长任务大多采用纯值快照、worker 独立数据库连接和 queued completion。
4. Python 任务由 `ExternalModelTaskRunner` 统一启动，任务中心不直接操作 Python 进程。
5. 评估引擎、ViewModel 和 QML 面板通过注册表扩展，检测/分割/异常边界清晰。
6. FS-SAM2 复用普通模型任务链，避免 feature 模块出现第二套训练调度系统。
7. 参数和设置以 YAML、动态 provider 和统一字段模型驱动，降低固定 C++ 参数类数量。
8. 测试使用 CTest、fixture、环境注入和项目级真实文件流程，而不是只测试孤立函数。

## 12. 当前最值得优先处理的问题

以下排序基于静态代码、CMake、配置和测试审计。标记为“可能”“未见”的问题尚未由真实桌面场景完全确认，不在证据不足时升级为 P0。

### P0

暂无已确认事项。当前分析未发现已经证实的不可恢复数据丢失、全局启动失败或安全事件。若项目重开、删除或退出 smoke test 证实存在数据丢失或不可恢复状态，再重新评估优先级。

### P1

#### P1-1 项目图片基础路径打开后可能未恢复

- **问题**：打开已有项目时，数据库中的 `image_base_path` 可能没有正确回写到 `Project` 内存状态。
- **代码位置**：`src/project/Projects.cpp` 的 `Project::openProject()`；`src/project/include/project/Projects.h`；`src/database/Repositories/ProjectRepository.*`；`ProjectDataBase` 项目打开接口。
- **为什么是问题**：当前打开流程将 `image_base_path_` 传入数据库接口，而相关接口存在值传递语义，数据库读取值可能无法回写到 `Project` 成员。
- **影响范围**：已有项目重新打开、图片缩略图、数据集浏览、标注加载、导入导出和模型数据准备。
- **建议改法**：让项目打开接口返回完整项目记录或明确的加载结果，由 `Project` 一次性更新内存状态并发出通知；增加“写入路径、关闭、重新打开、验证路径”的回归测试。
- **是否值得现在修改**：是。属于项目基础状态正确性问题，应优先处理。

#### P1-2 导入写库绕过 database 门面

- **问题**：`ImportDatabaseWriter` 直接操作 DDL、sqlpp11 connection 和 transaction，绕过 `ProjectDataBase` 与 Repository。
- **代码位置**：`src/data/ImportDatabaseWriter.cpp`；`src/database/DataBase.cpp`；`src/database/ProjectDataBase.*`；`src/database/Repositories/`；`src/database/include/database/ddl/`。
- **为什么是问题**：形成第二套数据库写入入口，事务边界、错误处理、schema 演进和连接配置可能与 `database` 模块不一致，违反数据库访问集中原则。
- **影响范围**：数据集导入、类别/图片/标注写入、数据库迁移、导入失败回滚和未来 schema 修改。
- **建议改法**：将导入所需的聚合写入操作收敛到 `ProjectDataBase` 或数据库 Repository；`data` 模块只提交导入结果和纯值数据，由数据库层统一管理事务。
- **是否值得现在修改**：是。这是最明显的架构分叉点，越晚处理，后续 schema 和导入功能成本越高。

#### P1-3 删除语义与 SQLite foreign key enforcement 未统一

- **问题**：不同删除路径的级联清理语义不一致，且未明确确认所有 SQLite connection 都启用了 foreign keys。
- **代码位置**：`src/database/Repositories/DatasetRepository.cpp`；`src/database/Repositories/LabelRepository.cpp`；`src/data/DataManager.cpp`；`src/database/include/database/ddl/`；`src/database/DataBase.cpp`。
- **为什么是问题**：部分路径只删除单表，部分路径才清理图片、标注和标签关系，可能留下孤儿记录或产生不一致错误。
- **影响范围**：数据集删除、图片删除、标签删除、项目重载、统计结果、导出结果和数据库长期一致性。
- **建议改法**：集中项目数据聚合的删除入口；在统一数据库层启用并验证 `PRAGMA foreign_keys = ON`；通过事务执行级联删除；增加删除后无孤儿记录的测试。
- **是否值得现在修改**：是。这是潜在数据完整性问题；在确认实际数据丢失前暂不升级为 P0。

#### P1-4 应用退出没有明确经过项目和任务关闭流程

- **问题**：应用退出路径可能绕过项目及任务控制器的有序关闭。
- **代码位置**：`src/tool/qml/Main.qml`；`src/project/Projects.cpp` 的 `Project::shutdown()`；`src/model/ModelTaskController.*`；`src/model/ModelTestTaskManager.*`；`src/model/ExternalModelTaskRunner.*`。
- **为什么是问题**：`Main.qml` 的退出动作直接调用 `Qt.exit(0)`，资源收敛主要依赖 singleton 或析构路径，外部 Python 进程、线程、取消令牌和迟到回调可能未完成收敛。
- **影响范围**：训练/推理期间退出、外部进程残留、任务状态、数据库释放、未完成文件写入和下次启动。
- **建议改法**：统一为“请求退出 → `ProjectManager` 关闭项目 → 控制器停止并等待 → 释放数据库 → 最后退出 Qt”；关闭入口必须幂等，并忽略终态任务的迟到事件。
- **是否值得现在修改**：是。长时间训练任务发布前应优先确认并处理。

#### P1-5 构建、开发运行和发布使用多套目录语义

- **问题**：构建产物、QML module、Python 文件、外部 DLL 和安装包使用多套路径布局。
- **代码位置**：根目录 `CMakeLists.txt`；`cmake/AddPluginLibrary.cmake`；`tools/link_dependencies.py`；`tools/package_app.py`；各模块 QML module 和安装规则。
- **为什么是问题**：开发目录能运行不代表干净机器上的 DLL、QML module、Python 任务和 InferRT/CUDA 依赖都能被正确发现。
- **影响范围**：Windows 发布包、安装后启动、自定义 build directory、QML 加载、Python 任务和外部运行时。
- **建议改法**：以 CMake install/runtime layout 作为唯一事实源，打包脚本读取安装清单或 manifest，不再独立维护路径推导；增加干净 staging 目录的启动和最小任务 smoke test。
- **是否值得现在修改**：是，但排在数据一致性和关闭流程之后；若近期没有发布计划，先建立发布 smoke test。

#### P1-6 顶层页签与页面数组不一致

- **问题**：`Header.qml` 有 7 个页签，而 `Content.qml` 只有 6 个页面，“导出”页签没有对应页面。
- **代码位置**：`src/tool/qml/Header.qml`；`src/tool/qml/Content.qml`；`src/tool/qml/Main.qml`。
- **为什么是问题**：点击“导出”后，`currentIndex` 可能超出实际页面范围，用户进入无效或空白页面。
- **影响范围**：顶层导航、导出功能入口、当前页面状态和 QML index 绑定。
- **建议改法**：以一个导航条目模型作为页签和页面的唯一事实源；如果导出功能尚未存在，应移除无效页签，而不是保留空入口。
- **是否值得现在修改**：是。属于直接可见、修改范围小的用户界面缺陷。

### P2

#### P2-1 项目属性通知可能与内存状态脱节

- **问题**：项目描述和图片基础路径的通知声明，与实际更新当前 `Project` 成员的路径可能不完整。
- **代码位置**：`src/project/include/project/Projects.h`；`src/project/Projects.cpp`；项目基础信息更新路径；最近项目模型和数据库更新路径。
- **为什么是问题**：调用方可能收到通知但读到旧值，或者数据库已更新而 QML 仍显示旧状态。
- **影响范围**：项目设置页面、QML 属性绑定、最近项目列表和项目重新打开行为。
- **建议改法**：统一项目属性写入口，先更新内存状态，再持久化并发出对应通知；为描述和图片基础路径分别增加可观察行为测试。
- **是否值得现在修改**：值得在处理 P1-1 时一并核对；没有复现前不建议单独大范围重构。

#### P2-2 GUI 线程仍存在同步数据库和文件操作

- **问题**：项目打开、最近项目、设置加载和部分数据模型 CRUD 可能直接在 GUI 线程执行。
- **代码位置**：`src/project/Projects.cpp`；`src/settings/GlobalSettings.cpp`；`src/settings/SettingsDataBase.cpp`；`src/data/DataManager.cpp`；相关 Repository 调用路径。
- **为什么是问题**：大数据集或 SQLite 锁竞争时会阻塞界面，与后台 I/O 的既定边界不完全一致。
- **影响范围**：项目打开、设置对话框、数据集页面、批量 CRUD 和并发导入导出。
- **建议改法**：先测量耗时和锁等待，确认热点后将重量级读取/写入迁移到 worker；GUI 线程只负责 QObject、Qt Model 和状态更新。
- **是否值得现在修改**：先做 profiling 和最小化验证，不建议在没有性能数据时全面迁移线程。

#### P2-3 模型与依赖配置存在多套事实源

- **问题**：模型可运行条件分散在模型注册表、YAML、参数解析、任务准备、评估注册、EasyTrain、CMake 和依赖 manifest 中。
- **代码位置**：`config/models/`；`src/model/`；`src/model/EvaluationEngineRegistry.*`；`3rdparty/EasyTrain/`；`tools/dependencies.yaml`；CMake 依赖配置。
- **为什么是问题**：新增或修改模型时，容易出现编译可用但运行不可用，或开发环境可用但发布包缺少依赖。
- **影响范围**：新增模型、模型参数、训练/测试任务、评估、Python 环境和发布包。
- **建议改法**：明确模型配置唯一事实源，为注册表、参数、任务能力和评估能力增加一致性检查；优先增加校验，不要先重写整个模型模块。
- **是否值得现在修改**：值得规划，但应在 P1 数据和生命周期问题收敛后处理。

#### P2-4 关键异常、取消和资源释放场景测试不足

- **问题**：正常数据流覆盖较多，但 Python 失败/取消、损坏数据库和图片、QML engine teardown、多项目隔离、provider 生命周期及真实桌面退出覆盖不足。
- **代码位置**：`tests/common`；`tests/data`；`tests/model`；`tests/model_qml`；`tests/project`；`tools/run_project_tests.py`。
- **为什么是问题**：P1 生命周期、数据库一致性和发布问题缺少足够的回归保护，修复后仍可能在边界场景回归。
- **影响范围**：任务生命周期、项目关闭、外部进程、数据库完整性、QML 状态和发布验证。
- **建议改法**：针对高风险问题增加少量行为测试：项目重开路径恢复、删除后的关联记录、Python 取消、退出时进程收敛和干净发布目录启动；避免先扩大全量测试矩阵。
- **是否值得现在修改**：是，但只做与 P1 改动直接对应的测试。

#### P2-5 公共递归扫描工具存在实现疑点且缺少行为覆盖

- **问题**：`common::Utils` 的递归文件/目录扫描存在递归条件和参数传递疑点，测试没有系统覆盖扫描边界。
- **代码位置**：`src/common/Utils.*`；`tests/common`；`src/data/DataImportService.cpp` 及各格式 importer。
- **为什么是问题**：扫描错误会导致数据集、图片或 Mask 被漏读、误读或重复处理，调用方补丁会进一步扩大分叉。
- **影响范围**：Folder 导入、数据集发现、图片/Mask 扫描、模型文件查找和路径处理。
- **建议改法**：先用临时目录行为测试覆盖空目录、嵌套目录、扩展名过滤和扫描失败；确认问题后修正公共实现，不在调用方添加特例。
- **是否值得现在修改**：值得先验证；如果确认影响当前导入流程，应升级为 P1。

#### P2-6 QML 装配和全局进度状态仍有维护性问题

- **问题**：QML glob 未使用 `CONFIGURE_DEPENDS`，`Main.qml` 存在 `parent.heght` 拼写错误，全局 `ProgressManager` 只维护单个活动进度任务。
- **代码位置**：`src/tool/CMakeLists.txt`；`src/tool/qml/Main.qml`；`src/ui/ProgressManager.*`。
- **为什么是问题**：新增 QML 文件可能不会触发重新配置，拼写错误可能导致布局或绑定失效，多个并行任务的进度状态可能相互覆盖。
- **影响范围**：QML 增量构建、顶层布局、并行导入/训练/评估任务和进度展示。
- **建议改法**：先修复确定性的 glob 配置和拼写错误；对多任务进度需求先确认产品语义，再设计按任务身份管理的状态，而不是继续增加全局特例。
- **是否值得现在修改**：确定性错误值得顺手修复；多任务进度应在有明确需求和复现后单独设计。

#### P2-7 文档索引存在过期入口

- **问题**：部分文档仍引用当前 docs 目录中无法读取的 `REFACTOR_SPEC.md`、`final_plan.md`、`refactor-tickets` 和访谈文件，根 README 的 CMake 版本说明也可能低于实际要求。
- **代码位置**：`docs/README.md`；`docs/ARCHITECTURE.md`；`docs/DEVELOPMENT.md`；根目录 `README.md`。
- **为什么是问题**：开发者会被引导到不存在的设计或实施文档，增加理解架构和领取任务的成本，也容易形成第二套事实源。
- **影响范围**：开发 onboarding、架构改造、任务领取和后续维护。
- **建议改法**：只保留可访问的导航；文档只维护索引和稳定约定，接口、目标、参数和数据库结构继续指向源码、CMake、DDL 和 YAML。
- **是否值得现在修改**：值得顺手清理，但不应阻塞功能修复。

## 14. 分析依据
